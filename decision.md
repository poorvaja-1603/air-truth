# decision.md

Technical decision log for AirTruth Mumbai. Format follows the brief. Status words such as PENDING appear inside the second column. Superseded decisions are kept and marked.

Last updated: 31 October 2026 (CA1 implementation complete, microproject pending).

| Decision | Selected Approach | Reason | Alternative Considered |
|---|---|---|---|
| D01 Project idea | AirTruth Mumbai: reconcile ground-station air quality, weather, and model estimates | Highest score (47 of 55) on usefulness, distinctiveness, verified tooling, and right size. The reconciliation and station-reliability angle gives real data engineering work (quality scoring, grain mismatch, late data) instead of a chart demo | Mandi price vs rainfall (fragile API), Rain x Tide flood risk (coarse ocean grid, no ground truth), rooftop solar, quake watch, stock dashboard |
| D02 Data source selection | OpenAQ v3 (ground truth), Open-Meteo Archive (weather), Open-Meteo Air Quality (model) | Each plays a distinct role: truth, explanation, estimate. All are free. Open-Meteo needs no key, OpenAQ needs a free key | Government portals directly (key and reliability issues), scraping station websites (fragile and against the spirit of the brief) |
| D03 Number of sources | Three feeds from two providers | Enough for real joins and reconciliation without exceeding what two people can finish in 16 days | One source only (too generic), five or more sources (scope risk) |
| D04 Geographic and time scope | About 8 Mumbai stations, 90 days of hourly data, ending 7 days before run date, 3-day overlap on daily runs | Small enough for free tiers and rate limits, large enough for incremental load behaviour. Seven-day offset avoids reanalysis latency. Overlap handles late-arriving station data | Whole of India (rate limits and effort), one year (needless volume), real-time only (no history for analysis) |
| D05 Extraction strategy (CA1) | `requests` with `urllib3.Retry`, exponential backoff, explicit status checks, rate-limit header handling, throttle at 50 calls per minute | Explainable in a viva, directly matches the CA1 error handling requirement, and respects the 60 per minute limit | OpenAQ Python SDK (hides retry behaviour we must explain), async clients (no benefit under a 60 per minute cap) |
| D06 API versus downloadable dataset | Live APIs | Brief lists API or CSV; APIs demonstrate retry, pagination, and rate limits, and they are what Airbyte will replace later | Downloading the Mendeley OpenAQ-derived dataset (static, stops at an earlier date, skips the extraction challenge) |
| D07 Cloud storage for CA1 (SUPERSEDED by D27) | Google Cloud Storage | Same Google Cloud project later hosts BigQuery: one account, one credential setup, native Parquet loading, 5 GB-months free in US regions | AWS S3 (valid under the brief, but adds a second cloud account only for CA1) |
| D08 File format | Parquet with Snappy, Hive-style `year=/month=` partitions | Keeps types, compresses well, enables column and partition pruning, loads natively into BigQuery. We will report measured compression on our own data | CSV (type loss, larger, no pruning) |
| D09 CA1 transformation approach | Pandas with a documented 13-rule specification (plan section 17) | Mandated by CA1. The rule table doubles as the specification for dbt later | PySpark or Polars (not required, more to explain) |
| D10 Imputation policy | Forward fill up to 3 hours for pollutants, linear interpolation up to 3 hours for weather, never beyond, with an `is_imputed` flag | Fixes brief outages without inventing long stretches of data, and the quality mart can report honest completeness | Mean replacement (flattens real spikes), dropping all gaps (fragments daily means), unlimited ffill (fabricates data) |
| D11 Source of business thresholds | `reference/pollutant_thresholds.csv`, read by Pandas and loaded as a dbt seed | One file means both phases cannot drift apart. Values to be confirmed against CPCB at M2 | Hardcoding thresholds in code and SQL separately |
| D12 Ingestion tool | Airbyte | OpenAQ source connector verified in its catalogue, Connector Builder available for Open-Meteo, free, Airflow operator exists | Fivetran: free plan exists, but no OpenAQ or Open-Meteo connector found, and custom sources need the Connector SDK |
| D13 Airbyte deployment (UPDATED) | Local `abctl` in normal mode, Cloud trial as fallback. Machine has 16 GB RAM and 20 cores, so local is viable and keeps the Connector Builder | Cloud keeps the laptop light and always has the Connector Builder. Local low-resource mode disables the Builder, which we need. Depends on laptop RAM and confirmed trial terms | Local `abctl` as the default (needs about 4 CPU and 8 GB RAM) |
| D14 Warehouse | Google BigQuery on a billing-enabled project (free trial or Free Tier) | 1 TiB queries and 10 GiB storage free per month, shares a project with GCS, serverless | Snowflake (trial duration unverified, separate account, no link to GCS) |
| D15 BigQuery mode | Not the sandbox | Sandbox has no DML or streaming and expires tables after 60 days, which can break dbt incremental models and Airbyte typed loading | Sandbox (free without a card, but functionally limited for this stack) |
| D16 Transformation tool | dbt Core with the BigQuery adapter | Free, tests and lineage built in, good demo value | dbt Cloud (extra account), raw SQL scripts (no tests or lineage) |
| D17 dbt model design | Staging (views), intermediate (views), marts (tables partitioned by date, clustered by station_id) | Staging stays source-faithful, marts answer business questions, intermediate holds the joins. Partitioning and clustering keep queries cheap | Single layer of tables (no separation of concerns) |
| D18 Airflow design | One DAG `airtruth_daily`: Airbyte syncs, then dbt staging and tests, then dbt marts and tests, then freshness check. Tests act as gates | Matches the required flow. Failed tests stop mart refresh so the BI never reads broken data | One task per dbt model via Cosmos (richer UI but extra dependency; optional later) |
| D19 How Airflow runs dbt | `BashOperator` calling dbt CLI | Simple and easy to explain | Astronomer Cosmos (more dependencies) |
| D20 Conversational BI | Streamlit app: question, LLM generates SQL against a curated schema description, `sqlglot` validates, BigQuery dry run, read-only execution, result table plus summary | Real natural-language-to-SQL against the warehouse as the brief requires, with controls that prevent destructive or expensive queries | Hardcoded answers (rejected by brief), warehouse-native conversational features (not verified for free or student access) |
| D21 BI safety controls | SELECT only, single statement, allow-list of mart tables, forced LIMIT, `maximum_bytes_billed`, read-only service account, query log | Defence in depth: no single control is trusted alone | Prompt instructions alone (not a security control) |
| D22 LLM provider (UPDATED) | Gemini, set through environment variables, confirm free-tier model id in AI Studio at M15 | Free-tier limits and model names have changed repeatedly in 2026, so the code must not depend on one provider | Hardcoding one provider |
| D23 Error handling and validation approach | Retry only retryable errors, fail fast on auth errors, non-zero exit or failed Airflow task on unrecoverable failure, row counts logged per stage | Meets the brief and the rule that failures are never hidden | Catch-all try/except that continues |
| D24 Use of Airflow in CA1 | Not used. Terminal logs as evidence | CA1 brief accepts terminal output. Keeps CA1 small and avoids pulling microproject work forward | Airflow DAG in CA1 (extra effort, not required) |
| D25 Excluded technologies | No Kafka, Spark, Kubernetes management | Data is small and hourly; no requirement justifies them | Streaming stack (complexity without benefit) |
| D26 Scope-cut order | Drop `mart_pollution_weather_drivers`, then chart auto-generation, then NO2. The required stack is never cut | Protects the explicit microproject requirements if time runs short | Cutting a required tool |
| D27 CA1 cloud storage | AWS S3, bucket layout `processed_data/year=YYYY/month=MM/`, least-privilege IAM user | User already has AWS credits and the CA1 brief allows S3. Supersedes D07. Loses the single-cloud convenience, so BigQuery loading from Parquet is no longer a fallback | GCS (needs a card-backed Google Cloud account just for CA1) |
| D28 CA1 scope | CA1 only does what the CA1 PDF lists: OpenAQ only, about 5 stations, 30 days, Pandas cleaning, Parquet to S3, evidence, report, video | Two-day window and the instruction to include nothing beyond the CA1 document. Weather, model data, and quality scoring move to the microproject | Full three-source CA1 (too much for 2 days, includes non-CA1 items) |
| D29 Warehouse (OPEN) | BigQuery preferred, Snowflake as fallback, pending whether a billing-enabled Google Cloud project is possible | BigQuery sandbox is unusable for this stack, so billing is required | Sandbox |
| D30 CA1 multi-source design | OpenAQ API (key, JSON, paginated) plus the Mendeley CSV (file download, CC BY 4.0), merged into one daily Parquet with a `source` column | Professor asked for multiple sources with different acquisition methods. The CSV adds history back to 2019 and a second real ingestion path, and station name matching and grain alignment are genuine integration work | Open-Meteo as second source (same REST method, and it belongs to the microproject), web scraping as the second source (terms unchecked, extra dependency) |
| D31 Initial dependencies | `requests`, `pandas`, `python-dotenv` only at M1. `pyarrow` and `boto3` are added at the milestones that need them | Rule of no unneeded dependencies. python-dotenv keeps keys out of code and shell history | Reading env vars only from the shell (error-prone on Windows) |
| D32 OpenAQ sensor selection | Select active sensors by sorting sensor IDs descending | OpenAQ v3 location endpoints contain both legacy (2019-2022) and active sensors; higher sensor IDs reliably designate current active sensors | Querying all sensors or hardcoding sensor IDs |
| D33 AWS temporary credentials | Pass `AWS_SESSION_TOKEN` to boto3 client alongside access key and secret key | AWS Academy / Learner Lab utilizes session tokens that rotate with lab sessions | Long-term IAM user credentials |

## Superseded decisions
